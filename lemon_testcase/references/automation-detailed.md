# 自动化测试设计详解

## 自动化边界

自动化候选表示“值得评估”，不是已经生成了可运行脚本。稳定、重复、高频、断言明确的案例优先；一次性探索、视觉主观判断、第三方不稳定或维护成本过高的案例保留人工执行。

## 分层模型

单元层验证纯逻辑；接口层验证契约和服务组合；组件层验证页面组件；UI 层覆盖关键路径；端到端层验证少量跨系统主链路。越靠上执行越慢、环境依赖越多，因此应把大多数规则放在较低层。

## 自动化案例字段

自动化建议至少记录 layer、data_strategy、isolation、wait_strategy、assertion_strategy、cleanup 和 maintenance_risk。没有清理策略的案例不能直接标记为高优先自动化。

## 数据管理

每个案例使用独立 fixture，动态邮箱、资源 ID 和 token 由 fixture 生成。测试结束清理创建的资源；清理失败要被报告，不得吞掉。共享只读数据可以复用，但必须明确不可变。

## 等待策略

优先等待明确条件、网络响应、状态变化或元素可交互。避免固定 sleep，因为它会使测试变慢且不稳定。等待超时信息应包含页面、请求、元素和最后观察状态。

## 断言策略

断言消息要说明业务对象、期望值和实际值。接口案例结合状态码、schema、关键字段和后续查询；UI 案例结合可访问名称、状态、文本和业务结果。截图只作为诊断材料，不能替代核心断言。

## 页面对象

页面对象封装定位器和操作，不把业务断言全部藏在页面对象里。选择器优先语义属性、可访问名称和稳定 data-testid；避免依赖易变 CSS 层级或文字装饰。

## 独立性

案例不得依赖另一个案例已执行。每条案例都能准备前置数据、执行动作和清理。执行顺序随机化可以帮助发现隐式依赖。

## 失败诊断

失败产物应包含请求上下文、脱敏响应、截图、日志、trace ID 和 fixture ID。重试只能用于已知瞬态错误，不能用来掩盖真实产品失败。

## CI 规划

提交阶段运行快速单元和接口冒烟；合并阶段运行关键 UI；夜间运行完整回归和性能测量。报告保留案例编号、版本、环境、依赖和失败原因。

## 维护治理

需求删除时同步删除或标记案例；连续不稳定的案例要记录原因；维护成本高于业务价值时降级为人工探索。自动化覆盖率不能只看数量，还要看风险和业务链路。
