# Diagnostic Decision Record

## 目的

Bug 分析常常在多人、多轮验证后完成。决策记录让后来者看到“当时知道什么、为什么选择这条路、哪些判断仍然不确定”，避免只保留最终结论而丢失推理过程。

## 最小结构

```yaml
decision_id: D-001
time: ISO-8601
question: "要判断的问题"
options: ["方案或假设 A", "方案或假设 B"]
evidence_refs: [E-001, E-002]
history_refs: [HIST-001]
decision: "当前选择或暂不选择"
reasoning: "因果关系与差异"
uncertainty: ["尚未验证的部分"]
next_action: "下一步验证"
owner: "负责人"
```

## 记录原则

1. 只记录当时可获得的证据，不用事后结果倒推当时的确定性。
2. 历史案例的影响必须单独列出，说明哪些部分可迁移、哪些不能迁移。
3. 排除一个假设也要记录验证证据，避免后续重复排查。
4. 业务规则不明确时，把决策交给业务负责人，不让模型擅自选择规则。
5. 涉及生产止血或数据操作时，记录授权、风险、回滚和观察指标。

## 常见决策节点

- 是否满足分析准入？
- 哪些缺失信息真正阻塞根因确认？
- 历史匹配是否足够相似，是否需要重新验证？
- 哪个验证动作能最大程度区分候选根因？
- 当前证据能否把假设升级为确认根因？
- 是否需要临时止血？
- 修复后是否满足回归和关闭门禁？

## 审计要求

决策记录应能关联 Bug、证据、假设、验证任务和 TestPilot 执行。没有关联 ID 的口头判断只能作为备注，不能作为关闭依据。

## 示例

```yaml
decision_id: D-014
question: "是否复用历史上的消费幂等根因"
options: ["直接采用历史结论", "把历史结论作为候选并重新验证"]
evidence_refs: [E-003, E-004]
history_refs: [HIST-014]
decision: "采用第二项"
reasoning: "业务流程和事件类型一致，但当前消费者版本与历史不同，且缺少当前重复投递证据。"
uncertainty: ["当前事件是否进入死信", "幂等键是否被错误复用"]
next_action: "查询 broker 投递轨迹并重放脱敏事件"
owner: "测试负责人"
```

这类记录应在验证完成后追加结果，而不是覆盖原始决策。这样可以复盘当时的信息边界，也能识别知识库中哪些历史结论需要重新审核。

## 保留规则

即使决策后来被推翻，也保留原记录、推翻证据和新决策 ID；删除历史判断会破坏根因知识库的审计价值。

记录内容应使用脱敏后的证据引用，原始敏感材料只保留在有权限的 TestPilot 存储中。

每次重新分析同一 Bug 时递增记录版本，并保留触发重新分析的新增证据。
