# Bug Analysis Operating Instruction

这份指令可直接作为测试人员提交给 `lemon-bug-analyser` 的分析请求模板。它规定输入方式、历史知识库声明、分析深度和交付格式，避免只给一句“帮我看看 Bug”。

## 推荐调用指令

```text
请使用 lemon-bug-analyser 分析下面的 Bug。

【分析模式】
- 模式：标准 / 完整 / 快速
- 是否允许调用 TestPilot 知识库：是 / 否 / 未连接
- 是否允许输出 TestPilot 验证任务：是 / 否
- 是否需要生成回归测试范围：是 / 否

【项目上下文】
- 项目：
- 版本：
- 环境：
- 模块：
- 功能/业务流程：
- 用户角色：
- 相关接口：
- 发生时间：
- 发生频率：稳定 / 偶发 / 一次 / 未知

【Bug 描述】
- 标题：
- 实际结果：
- 期望结果：
- 复现步骤：
  1.
  2.
  3.

【证据】
- traceId / requestId：
- 日志时间范围：
- 错误日志：
- 接口请求：
- 接口响应：
- SQL：
- 截图或录屏：
- 监控数据：
- 最近发布/配置变更：

【业务规则】
- 正常状态流转：
- 允许的状态转换：
- 不允许的状态转换：
- 幂等规则：
- 事务或最终一致性要求：

【输出要求】
请严格区分：
1. 当前输入直接证明的事实
2. TestPilot 历史知识库提供的证据
3. 测试专业知识推导出的候选假设
4. 尚未验证的内容

请不要在证据不足时直接确认根因。对每个候选根因给出：支持证据、反证、验证动作、预期结果、成本和停止条件。
```

## 快速模式

适用于普通 Bug 初判，只输出：

1. 初步结论和置信度
2. 关键事实
3. 最可能的 2-3 个原因
4. 优先排查步骤
5. 需要补充的信息
6. 回归重点

快速模式仍然必须说明是否调用了 TestPilot 知识库。

## 标准模式

适用于测试人员提交缺陷，输出：

1. 缺陷摘要
2. 影响范围和严重程度
3. 已知事实与证据
4. 未知信息
5. 历史案例匹配结果
6. 业务/接口/数据关联
7. 可能原因和验证方法
8. 日志、SQL、接口或监控排查方向
9. 修复建议
10. 回归范围

## 完整模式

适用于支付、订单、库存、数据一致性、性能、线上故障、安全或用户明确要求“详细分析”的情况。除标准模式内容外，还要输出：

- 分析准入状态
- 证据台账
- 关系链和断点
- 历史知识库命中字段与差异字段
- 假设状态：candidate / supported / rejected / verified / inconclusive
- TestPilot 可执行验证任务
- 临时止血、最小修复、长期治理
- 发布、回滚和监控方案
- 数据修复安全边界
- 回归验收标准
- Bug 关闭条件和观察期

## TestPilot 知识库声明规则

每次分析必须在开头明确写出以下字段：

```text
知识库状态：已连接 / 未连接 / 已提供离线导出 / 未知
是否实际检索历史案例：是 / 否
命中案例：案例 ID 或“无匹配”
历史证据：历史观察 / 历史推导 / 历史推断 / 历史已验证
当前案例是否复用了历史结论：是 / 否 / 仅作为候选
```

如果没有 TestPilot 连接器、历史文件或历史案例内容，必须写：

```text
本次分析未使用 TestPilot 知识库。
分析依据为当前输入证据和 lemon-bug-analyser 内置的测试专业规则。
```

当 TestPilot 在本机运行并允许只读访问时，使用：

```bash
python3 scripts/testpilot_api.py \
  --base-url http://127.0.0.1:3344 \
  --task-id <task_id> \
  --output testpilot-context.json
```

读取后必须把任务 ID、知识条目 ID 和状态写入分析的“知识库使用声明”。待审核知识不能当作已验证根因。

不得把 Skill 内置的专业规则描述成 TestPilot 历史知识。

## 历史命中后的处理要求

历史案例命中后，必须比较：

- 相同功能或业务流程
- 相同接口或错误指纹
- 相同触发条件和数据状态
- 相同环境和版本
- 历史根因是否有验证记录
- 当前案例与历史案例的差异

历史命中只能产生候选方向。当前 Bug 只有在当前证据和验证结果支持后，才能确认根因。

## 没有历史命中时的处理要求

必须切换到专业诊断模式：

1. 识别缺陷领域。
2. 构建功能、业务、接口、数据和依赖关系链。
3. 至少提出两个互相竞争的假设。
4. 为每个假设设计可执行验证。
5. 先执行高影响、强证据、低成本的验证。
6. 不能把“测试经验上的常见原因”写成当前 Bug 的事实。

## 日志和 SQL 请求模板

如果用户要求日志或 SQL 排查，必须分别回答：

### 日志

- 查询关键词
- 时间窗口
- Trace/Request ID
- 服务和线程
- 异常堆栈
- 重试和回滚
- 预期看到的结果
- 结果如何支持或排除假设

### SQL

- 当前数据查询
- 实际更新 SQL
- 影响行数
- 执行计划
- 索引
- 锁等待
- 事务边界
- 并发和幂等
- 只读检查与高风险写操作的边界

## 禁止输出

- 没有历史数据却声称“TestPilot 历史显示”。
- 只有一个错误日志却直接确认根因。
- 只有一条 SELECT 却断言 UPDATE 一定失败。
- 没有业务规则却擅自决定状态转换是否合法。
- 没有授权、备份和回滚方案就建议修改生产数据。
- 使用“检查一下”“优化一下”“加强监控”等不可执行表述。
